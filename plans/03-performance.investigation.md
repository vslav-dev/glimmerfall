# 03. Производительность на разных устройствах — исследование

Повод: новый телефон мощнее, но играть «хуже»; цвета непривычные. Цель — сутки собрать точные perf-данные, затем решать, что крутить.

## Что уже видно в телеметрии (13.11.2026)
- Новый телефон: dpr 3, 360×820 CSS → 1080×2460 физ., GPU Mali-G57 **MC2**, Chrome 157.
- Старый: dpr 2, 360×800, Mali-G57, Chrome 156.
- GPU того же класса, а пикселей у DOM в 2.25× больше.
- Поле рисуется с разрешением максимум 2 (`QUALITY[0]`) → холст 720 px в ширину, растянут ×1.5 до 1080 → поле мягче/мутнее, чем HUD. Вероятная часть «стало хуже».
- Одна сессия словила `contextlost` → `contextrestored`.

## Текущая архитектура (что влияет на скорость)
- Pixi 8, WebGL, цикл по требованию: кадры только пока что-то анимируется.
- Один атлас-текстура на всё поле, рисуется Canvas 2D под размер клетки и разрешение.
- Холст прозрачный поверх CSS-градиента → композитор смешивает полноэкранный слой каждый кадр.
- Автопонижение качества: 40 кадров > 24 мс → разрешение 2 → 1.5 → 1, частиц меньше. Тихое, необратимое до перезапуска, раньше не логировалось.
- `dt` обрезается до 50 мс → ниже 20 fps анимации замедляются, а не пропускают кадры.
- Свои rAF-циклы вне сцены: счётчики HUD (каждый кадр меняют `textContent` → layout), Glide; `offsetWidth` в `bump`/`flashText` — принудительный reflow.
- DOM: `drop-shadow`, тени, бесконечные CSS-анимации на титуле, анимация `pulse` при малом числе ходов.
- Генерация уровней — в воркере; на главном потоке: `advance` (шаг каскада), `JSON.stringify` сохранения, сборка атласа, пересборка спрайтов.

## Гипотезы
- Экран 90/120 Гц: сцена рисует чаще → больше нагрузки на слабый GPU; порог понижения 24 мс не срабатывает.
- Узкое место — заполнение пикселей (fill rate) Mali-G57 MC2 при dpr 3: DOM-слои + прозрачный холст.
- Рывки — от главного потока (layout HUD, сохранение, атлас), а не от GPU.
- Троттлинг от нагрева: медиана интервала растёт со временем сессии.
- Цвета: широкий цветовой охват (p3) экрана и режим «насыщенные» системы; не производительность.

## Набор логов (поток `perf`, + поля в `session`)
Принцип: агрегат вместо событий на кадр. ~1 событие на уровень.
- `session`: + `cores`, `memoryGb`, `gamut`, `hdr`.
- `perf/boot` (1 на сессию): TTFB, DOM ready, старт скрипта, сцена готова, игра готова; поддержка LoAF и Event Timing; куча JS.
- `perf/window` — шлётся при старте уровня, выходе в меню, сворачивании. Окно < 30 кадров переносится в следующее.
  - Контекст: уровень, размер поля, клетка, `dpr`, `res`, CSS-размер, реальные пиксели холста, ступень качества, настройки (размер поля, reduced motion), время сессии.
  - Интервалы кадров: p10 (≈ частота экрана), p50, p95, p99, max; число кадров > 20/33/50/100 мс; суммарное время анимации.
  - CPU кадра: обновление (твины, частицы) и отправка рендера Pixi — avg/p95/max. Остаток интервала = GPU/композитор/прочее.
  - Draw calls на кадр: avg/max — качество батчинга.
  - LoAF (кадры > 50 мс): число, сумма, блокировка, доля style/layout (DOM), худший кадр с самым долгим скриптом.
  - Ввод (Event Timing, > 40 мс): число, худший — задержка до обработчика / обработчики / до отрисовки.
  - `ops`: `atlas`, `rebuild`, `level` (загрузка уровня за шторкой), `draft` (воркер — бенчмарк CPU), `advance`, `persist` — n/сумма/max.
  - Куча JS (Chromium).
- `perf/quality`: каждое автопонижение — ступень, разрешение, время.

## Как читать через сутки
- p10 ≈ 8 → 120 Гц, ≈ 11 → 90 Гц, ≈ 16.7 → 60 Гц.
- p50 ≫ p10 при малом CPU (update+render) → упор в GPU/композитор → снижать разрешение/DOM-эффекты.
- Большой CPU render → много объектов/батчей; смотреть `draws`.
- Много LoAF с большим `layoutMs` → DOM (HUD-счётчики, reflow).
- `slow >50` > 0 → анимации замедлялись.
- Рост p50 со временем `t` → нагрев.
