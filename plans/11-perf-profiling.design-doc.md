# Глубокий профиль производительности (22.11.2026)

## Задача
- Найти точную причину остаточных медленных кадров (~2% на 0.25.1 против ~0,3% до бонусов).
- Шире: ответить, всё ли сделано для скорости, — замерами, а не догадками. Найденное по пути — чинить.

## Что уже меряется (plans/03, plans/10)
- Окно perf на уровень: интервалы кадров (p10…p99, >20/33/50/100 мс), CPU кадра (update, render), draw calls, LoAF, Event Timing, ops, куча.
- Флаги-кадры (зарядка, готовый бонус, свечение, прицел), взрывы по видам, пик частиц, батарея.
- Слепые зоны:
  - какой ресурс узкий в конкретном медленном кадре: GPU, главный поток до кадра, наш JS, DOM;
  - сколько пикселей рисуется за кадр (заливка — главный подозреваемый на Mali при dpr 3);
  - сколько кадров рисуется впустую;
  - флаги считают кадры, но не медленные кадры под флагом — связь не видна;
  - DOM-анимации HUD (счётчики, похвала) не видны вовсе.

## Что меряем (новое)
- **Профиль медленного кадра:** средние update, render, опоздание кадра, заливка, спрайты, частицы, отставание GPU — отдельно для медленных (>20 мс) и обычных кадров. Разница показывает узкое место.
- **Опоздание кадра:** насколько колбэк кадра начался позже начала кадра — главный поток занят до нас (DOM, GC, чужие задачи).
- **Отставание GPU (WebGL2):** забор после каждого рендера; через сколько кадров GPU его прошёл. ≥2 — упор в GPU.
- **Заливка:** площадь всех видимых спрайтов плюс очистка холста, в долях холста; гистограмма и доля медленных кадров по корзинам заливки.
- **Пустые кадры:** кадры, где из анимаций остались только паузы-ожидания: рисовать нечего.
- **Флаги с медленными кадрами:** для каждого флага — кадры и медленные кадры под ним.
- **DOM-активность:** флаги «катится счётчик HUD», «показана похвала».
- **A/B на устройстве:** в меню эффектов — выключатели DOM-эффектов (поп счётчиков, похвала, свечение бонуса); выключенные эффекты пишутся в окно perf.

## Что чиним сразу (найдено чтением кода)
- Кадры без видимых изменений (только паузы) больше не рисуются: цикл идёт, GPU отдыхает.
- Счётчики HUD писали текст каждый кадр прокрутки, даже без смены числа, — пишут только при смене.
- Перезапуск CSS-анимаций через принудительный reflow (`offsetWidth`) на каждом шаге каскада (поп счётчика, похвала) → Web Animations API без reflow.

## Кандидаты на потом (решать по новым данным)
- Холст размером с поле (+поля для эффектов) вместо всей сцены: меньше очистки и композитинга.
- Непрозрачный холст с фоном внутри: композитору не смешивать полноэкранный слой.
- Потолок частиц и размеры больших аддитивных вспышек.
- Ограничение частоты кадров для спокойных анимаций (подсказка) на 120 Гц.

- ✅ Флаги с медленными кадрами, DOM-флаги, выключенные эффекты в окне
- ✅ Выключатели DOM-эффектов в меню эффектов
- ✅ Пропуск отрисовки пустых кадров
- ✅ Счётчики без лишних записей текста; перезапуск анимаций без reflow

## Как читать новые окна (22.11.2026)
- `profile.slow` против `profile.fast`:
  - `late` заметно больше → главный поток занят до кадра (DOM, GC, чужие задачи): смотреть `flags` hudRoll/flashText и A/B выключателей;
  - `update`/`render` больше → наш JS;
  - `fill`/`sprites` больше, остальное то же → заливка, упор в GPU;
  - всё одинаково → время вне страницы: композитор, нагрев, троттлинг (сверять с `battery`, `flags.charging`).
- `gpuLag`: основная масса в 0 → GPU успевает; сдвиг в 2+ → GPU не успевает.
- `fillBins`: доля медленных по уровням заливки растёт → заливка виновата; ровная → нет.
- `flags.<имя>.slow / frames` против общей доли медленных → вклад состояния.
- `idle`: сколько кадров теперь не рисуется (паузы).
- `fxOff`: окна с выключенными эффектами для A/B на одном телефоне.

## Разбор окон 0.25.2–0.29.0 (22.11.2026)
- Данные: телефон игрока, 23 окна уровней на 0.25.2+, ~172 тыс. кадров; всё время на зарядке (14→44%).
- Кадры дольше 20 мс по версиям:
  - 0.22–0.24 — 0,26–0,44%;
  - 0.25.0 — 10,6%;
  - 0.25.1 — 3,7%;
  - 0.25.2+ — 0,8%; >33 мс — 0,14% (до бонусов было 0,04–0,06%).
- Ощущение «стало лучше» подтверждается: почти уровень до бонусов, в разы лучше 0.25.x.
- Пустые кадры: ~25% кадров больше не рисуются (паузы).
- Где медленные кадры:
  - 94% — во время прокрутки счётчика HUD, то есть во время каскада: 1,74% против 0,15% вне его;
  - вне каскадов лучше, чем до бонусов (0,15% против ~0,3%).
- Наш код не узкое место: в медленном кадре update ~0,3 мс, render ~1,2 мс; заливка и число спрайтов те же, что в обычном кадре.
- Опоздание кадра в медленных кадрах больше на 1–4 мс: немного работы главного потока после кадра (DOM HUD), но не основная часть.
- `gpuLag`: глубина очереди растёт при непрерывной анимации и в спокойных окнах с низкой долей медленных кадров тоже. Это глубина конвейера Chrome, а не признак упора.
- Остаток объясняется нагрузкой каскада:
  - бомб вдвое больше с 0.25.0;
  - потолок частиц (320) достигается почти в каждом окне;
  - телефон греется на зарядке.
- Ошибок и потерь контекста с 0.25.1 нет; качество не снижалось (res 2).
- Обновление сработало: found → applied за 1–10 с, дважды.

## Решение (22.11.2026)
- Код не меняем: дешёвых правок с заметным выигрышем данные не показывают.
- Отвергнуто:
  - glow попа счётчика через фильтр вместо text-shadow: число и так перерисовывается каждый кадр прокрутки, выигрыша нет;
  - снижение потолка частиц: спрайтов в медленных и обычных кадрах поровну, причина не в них;
  - непрозрачный холст с фоном внутри: выигрыш средний и не доказан, а риск — швы фона и переход темы. Вернуться, если A/B покажет упор в GPU вне DOM.
- Следующий замер — A/B на устройстве:
  - несколько уровней с выключенными «поп счётчиков» и «похвала»;
  - отдельно — не на зарядке.
- Сравнить долю медленных кадров во время каскада (флаг `hudRoll`) с текущими 1,74%.

## Пересмотр: что было не так и рефакторинг (22.11.2026)
### Ошибка прошлого разбора
- Вопрос ставился как «вернулись ли к уровню до бонусов», а не «где кадр тратит ресурс».
- Меряли только медленные кадры одного быстрого телефона. Работа, которая укладывается в кадр, но греет и тратит заряд (на слабых машинах она и есть просадка), не искалась.
- Пробелы телеметрии:
  - нет флага каскада: «счётчик крутится» подменял его, и вклад DOM от вклада поля не отделить;
  - не видно, сколько кадров рисуется ради медленных фоновых пульсаций;
  - работа компоновщика вне нашего цикла (CSS-анимации на простое) не видна вовсе.

### Найдено чтением кода
- Подсказка хода пульсирует бесконечно на полной частоте экрана (120 Гц), пока игрок думает; так же пульсируют прицел и подсвеченные бонусы. Это основное время игры.
- Ореол готового бонуса дышит бесконечной CSS-анимацией: компоновщик перерисовывает весь экран 120 раз в секунду на простое, пока бонус готов, то есть почти всегда.
- Поп счётчиков HUD анимирует text-shadow: анимация уходит с компоновщика на главный поток, число перерисовывается с размытием каждый кадр каждого шага каскада.
- Катящееся число пишется в DOM 120 раз в секунду: каждый раз стиль, раскладка, отрисовка.
- Тень полосы очков полностью срезана её же clip-path: перерисовывается без видимого эффекта.
- Лесенка качества при нехватке сразу снижает разрешение (картинка мутнеет), хотя на 120 Гц экране дешевле сначала рисовать ровные 60 кадров.

### Решения
- Спокойные кадры:
  - медленные фоновые движения помечаются спокойными (пульс подсказки, прицела, подсвеченных бонусов);
  - пока на экране движутся только они, кадр рисуется ~30 раз в секунду; GPU и компоновщик отдыхают;
  - любое обычное движение возвращает полную частоту.
- Темп 60 кадров: новая первая ступень лесенки качества для экранов чаще 60 Гц. Разрешение снижается только после неё.
- Ореол бонуса делает три вдоха после каждого хода и затихает горящим.
- Свечение попа — фильтр drop-shadow вместо text-shadow: transform и filter идут на компоновщике.
- Катящееся число пишется не чаще ~60 раз в секунду.
- Тень полосы очков убрана: видимого эффекта не было.
- Телеметрия:
  - флаги `cascade` и `calm`;
  - темп кадров в окне и в событии смены качества.

### Чек-лист
- ✅ Спокойные кадры в сцене (твины и апдейтеры), подсказка/прицел/подсветка — спокойные
- ✅ Ступень 60 кадров в лесенке качества для экранов с высокой частотой
- ✅ Ореол бонуса: конечное дыхание
- ✅ Поп счётчиков на компоновщике, запись числа ≤60 в секунду, тень полосы убрана
- ✅ Флаги `cascade`, `calm`; темп кадров в окне
- ✅ tsc, eslint, тесты, сборка

## 0.30.0: регресс в каскадах и телеметрия глубже (22.11.2026)
### Данные 0.30.0 (8 окон, уровни 113–120)
- Медленных кадров 0,9–9,7%, на 0.29.2 было 0,1–2,3%. Почти все в каскадах: 6–13% кадров каскада против ~1%.
- В каскадах с 0.30.0 изменилось одно: свечение попа счётчиков HUD стало фильтром drop-shadow вместо text-shadow. Остальное касается простоя.
- Вывод: фильтр — размытый слой на GPU на каждом попе каждого шага; на Mali это дороже перерисовки text-shadow. Предположение «на компоновщике дешевле» не подтвердилось.
- Спокойные кадры работают: подсказка рисуется ~30 раз в секунду (флаг `calm`).
- Ступень 60 кадров не включилась: доля медленных кадров ниже порога снижения качества.

### Решения
- Свечение попа — снова text-shadow, как в 0.29.2. Запись числа ≤60 раз в секунду остаётся.
- Слияние ряда в бонус: шло с ускорением (медленный старт, рывок в конце) — это было в коде, а не торможение. Теперь старт быстрый с плавной посадкой, чуть короче; бонус появляется, как только ряд собрался.
- Кольцо вспышки кнопки бонуса было не по центру: правило `box-sizing` не касалось псевдоэлементов, рамка кольца увеличивала его и сдвигала. Правило распространено на псевдоэлементы.
- Подвисание при запуске двойного бонуса: в коде есть намеренная пауза «сбор силы» перед комбо. Остальное покажут новые метрики — фазы и спайки.

### Телеметрия (новое)
- `work` и `after` в профиле медленных и обычных кадров, плюс гистограмма `after`:
  - сколько главный поток был занят в промежутке перед кадром;
  - `after` — работа после нашего кадра до освобождения потока: код после завершённых анимаций, другие колбэки кадра, стиль, раскладка, отрисовка DOM;
  - медленный кадр с малым `work` — ожидание GPU или компоновщика.
- `phases`: кадры, медленные кадры и худший кадр по тому, что играет поле: комбо каких бонусов, удар бонусом, взрыв, падение, обмен, создание.
- `spikes`: до 8 самых долгих кадров окна (>33 мс) со всем контекстом — `work`, `after`, опоздание, update/render, спрайты, заливка, фаза текущего и предыдущего кадра, включённые флаги.

### Чек-лист
- ✅ Свечение попа — text-shadow
- ✅ Слияние в бонус: быстрый старт, короче, бонус сразу по сборке
- ✅ `box-sizing` для псевдоэлементов
- ✅ Телеметрия: `work`/`after`, `phases`, `spikes`
- ✅ tsc, eslint, тесты, сборка

## Разбор 0.30.1 и итог (22.11.2026)
### Данные (9 окон, уровни 121–124, плюс вся сессия с 16:16)
- Медленных кадров 0,2–4,6%. По версиям не объясняется:
  - доля медленных кадров идёт за «стоимостью кадра»: время update+render обычного кадра на 100 спрайтов при том же коде;
  - стоимость 0,28–0,45 → медленных ≤0,5%; 0,55–0,78 → 2–10%;
  - тот же код считается в 1,5–2 раза дольше: процессор сбавил частоту.
- Это перегрев (троттлинг): телефон заряжался всю сессию, 4+ часа игры.
- Рост начался на 0.29.2 (17:41–17:44, 1,4–2,3%) — до выхода 0.30.0.
- Поправка к разбору 0.30.0: регресс там в основном нагрев. Вклад фильтра drop-shadow не доказан. Откат на text-shadow оставлен как более дешёвый вариант по коду.
- Медленные кадры:
  - главный поток занят 5–8 мс (обычные 2,3–3,3), то есть даже на нагретом телефоне большая часть промежутка — не наш код;
  - длинные кадры — ровно 4–6 периодов экрана (33,5 / 41,9 / 50,3 мс) при малой работе: ожидание GPU или компоновщика.
- По фазам:
  - взрывы 7–9% медленных (линии, бомбы), призма до 23%;
  - падение, совпадения, создание — ~2,7%;
  - обмен — 0,2%; простой — 0,5%;
  - комбо не хуже обычных взрывов (2–6%): отдельного подвисания комбо в данных нет, есть намеренный «сбор силы».
- Единичные пики главного потока до 40 мс — в начале совпадения после обмена. Редко, на плавность не влияют.

### Решения
- Пейсинг вместо постоянной ступени 60 кадров:
  - экран с высокой частотой, где кадры начали срываться (≥4 медленных из 120 движущихся), рисует ровные 60;
  - после серии чистых блоков возвращается на 120. Серия удваивается при каждом повторном включении, чтобы не дёргать туда-обратно;
  - лесенка качества — снова только разрешение и частицы.
- Телеметрия возвращается к рабочему объёму:
  - убраны спайки, корзины заливки и GPU-заборы (заборы давали глубину конвейера Chrome, а не упор);
  - убран одноразовый отчёт о вибрации (поток debug);
  - оставлены: профиль медленных и обычных кадров с `work`/`after`, `phases`, флаги (+ `paced`), счётчики (+ включения пейсинга), пики, батарея, пустые кадры.
- Дальше по производительности: код — не узкое место. Остаток — GPU нагретого телефона во взрывах; пейсинг закрывает именно его.
